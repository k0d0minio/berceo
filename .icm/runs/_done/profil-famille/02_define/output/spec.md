# Spec: The family's profile

- complexity: standard

## Problem

A family account holds a first name, a surname, an e-mail and a phone number (comptes-neon-auth),
and nothing else. The next stubs cannot work without two more facts. A care request is published
for a commune (demande-de-garde, D-20), and a professional needs the family's exact address once a
booking is confirmed (candidature-et-reservation, D-15). No commune reference exists in the
codebase yet. Stubs 4, 7 and 15 all match families to professionals by commune or postcode (D-11),
so this run also fixes the reference they share. This advances the Plateforme Berceo V1 objective:
a first usable version on uat.berceo.be before December 2026, for a launch in January 2027.
Cahier des charges C-04 ("compléter mon profil famille") and C-05 ("modifier mes informations").

## Proposed change

**Where.** A new page `/espace/famille/profil` in the family's space, guarded by
`requireAccess(SPACES.parent)` like the space's home. `SpaceShell` gains a "Mon profil" entry in the
portal navigation for the parent role, next to the home entry. The page is `noindex`, like every
space page.

**What the family sees and edits.** One form, prefilled from what is stored:

- **Prénom, nom** — required, trimmed, the same rules as sign-up. Saved on the `users` row.
- **Téléphone** — required, normalised to E.164 by the sign-up's `normalizePhone`. Stored and never
  verified by SMS (D-27). Saved on the `users` row.
- **E-mail** — shown and **not editable**. Neon Auth does not support changing an account's e-mail
  address yet ("Email address changes are not currently supported", Neon Auth user-management
  guide). A short line under it says the e-mail cannot be changed for now. The change is parked as
  a triage stub (`triage/famille-changement-email`) to build once Neon Auth supports it.
- **Commune** — required. A combobox searches the official list of Belgian localities by postcode
  or by name, and the family picks one entry, e.g. « 1050 Ixelles ». Only an entry of the list is
  accepted; the server rejects any other value.
- **Adresse** — optional in this run: rue, numéro, boîte. It is located in the postcode and
  locality chosen above, so the commune and the address can never disagree. If the rue or the
  numéro is given, both are required; the boîte is optional and only accepted with them. A line
  under the fields says the address is only shared with the professional once a booking is
  confirmed (D-15). Candidature-et-reservation asks for it at confirmation if it is still missing.
- **Quelques mots sur votre famille** — optional, at most 300 characters. The hint under it asks
  the family not to include health information or their children's names (D-20). This run only
  stores it; showing it to professionals is for demande-de-garde and candidature-et-reservation.

The form is a server action. The user's id always comes from the session, never from the form.
Errors are shown inline per field, in the catalogue's words. A successful save shows a confirmation
line on the page. The same form serves the first completion and every later edit.

**The family's home.** `/espace/famille` shows a "Complétez votre profil" block with a link to the
profile page as long as no commune is saved, and stops showing it once one is. The home's lists of
requests and past gardes come with stubs 7 and 11; this run adds nothing there.

**The commune reference.** `src/lib/communes/` holds the official list as a generated, committed
data module: every Belgian postal locality (postcode, locality name) with its commune (INS / REFNIS
code and name). It is built from bpost's public postcode list, joined to Statbel's REFNIS codes,
using the communes in force on the source's date (the 2025 Flemish mergers included). A script in
`scripts/communes/` regenerates it, and the module's header records both source URLs and the date.
The module is plain text (TS or JSON) and stays small, well under 1 MB, so it is not an archive or
a binary. It exposes: search by postcode prefix or name (accent- and case-insensitive), lookup by
postcode + locality, and the INS code of an entry. The family's commune for matching is that INS
code. Stubs 4 (the communes a professional serves), 7 and 15 reuse this module; it has no
family-specific code. Names are the French forms bpost gives, and the Dutch or German name where no
French form exists.

**Data model (one migration, generated by drizzle-kit).** A new `family_profiles` table, one row per
parent, created at the first save:

- `user_id` — uuid, primary key, references `users.id`, `on delete cascade`.
- `commune_ins` (text, not null), `postcode` (text, not null), `locality` (text, not null).
- `street`, `house_number`, `box` — text, nullable. These are the address.
- `context` — text, nullable, at most 300 characters (checked in the app and by a database check).
- `created_at`, `updated_at` — timestamptz.

These fields stay off `users`: `currentUser()` loads the whole `users` row on every request and
hands it to every page and shell, so an address there would travel everywhere the user object
goes. A separate table keeps the address behind one reader.

**Who can read the address (D-15).** `src/lib/famille/` (server-only) is the only module that reads
the address columns, through a function that returns the owner's own profile for their own page.
It also exposes a commune-only reader (INS code, postcode, locality) for the later stubs. Revealing
the address to a professional after a confirmed booking is candidature-et-reservation's; it adds its
reader to this module. A test fails if any file outside `src/lib/famille/` names the address
columns.

**Neon Auth's name.** The `users` row is the source of truth for first name and surname. If
`@neondatabase/auth` lets the server update the signed-in user's `name`, the save keeps it in step
(`"<prénom> <nom>"`, as at sign-up); if it does not, only the row changes. That is harmless, because
every e-mail after sign-up greets from the row.

**Words (D-19).** Every visible word lives in a new `src/content/famille.ts`, keyed by locale. Every
entry not quoted from Surya's guide carries `@relecture Surya`. Vouvoiement, no `!`, `…` or `—`,
and the "Mon profil" navigation label sits with the other space labels in `src/content/comptes.ts`.

**Look (D-9).** The DA's tokens and the retuned shadcn components only. No red or green outside a
confirmation dialog (D-24); this page has none.

## Acceptance criteria

- [ ] A signed-in parent opens `/espace/famille/profil` from the "Mon profil" entry in the portal navigation, on a phone (360 px wide, no horizontal scroll) and on a desktop.
- [ ] A professional or an admin who opens `/espace/famille/profil` is sent to their own space, and a signed-out visitor is sent to sign in with a return to the page; `routing.test.ts` covers the path.
- [ ] The form is prefilled with the parent's prénom, nom and téléphone. Saving new values updates the `users` row and `updated_at`, and the new first name is used by the space's greeting.
- [ ] The e-mail is shown and cannot be edited, with a line saying it cannot be changed for now; the server action ignores any e-mail field sent to it.
- [ ] Typing a postcode prefix (« 105 ») or a name, accents and case ignored (« ixel »), lists the matching localities; picking « 1050 Ixelles » and saving stores that postcode, locality and Ixelles' INS code.
- [ ] A commune value that is not an entry of the list, sent directly to the server action, is refused with a field error and nothing is saved.
- [ ] Saving without a commune is refused with a field error. Saving with a commune and no address succeeds; a rue without a numéro, a numéro without a rue, or a boîte alone is refused with a field error.
- [ ] A family completes the commune and address once, returns later, sees them prefilled, edits them, and the edit is saved.
- [ ] The context line accepts at most 300 characters and is refused above that, both in the form and by the database; the hint asks not to include health information or children's names.
- [ ] `/espace/famille` shows the "Complétez votre profil" block with a link to the profile while no commune is saved, and no longer shows it once one is.
- [ ] The address columns are read only inside `src/lib/famille/`: a test fails if another file names them, and a unit test proves the commune-only reader returns no address field. No page, action, route or API a professional or a visitor can reach returns the address.
- [ ] The server action saves only the signed-in parent's own rows, whatever user id the form carries, and refuses any non-parent session.
- [ ] `src/lib/communes/` contains the generated list with both sources and the date in its header, a script in `scripts/communes/` regenerates it, and tests cover search by postcode prefix, search by name, lookup and the INS code of a sample locality in each region (Brussels, Wallonia, Flanders).
- [ ] The migration adding `family_profiles` is generated by drizzle-kit, the journal test passes, and a preview build applies it to its own Neon branch through `vercel-build`, with `db:verify` passing.
- [ ] Every visible word of the profile page and the home block lives in `src/content/`; each entry not verbatim from the guide carries `@relecture Surya`; no entry uses `!`, `…` or `—` (a catalogue test enforces it).
- [ ] The e-mail-change triage stub exists under `.icm/intake/triage/`, naming the Neon Auth limitation and what the change must do once it is supported.

## Out of scope

- Changing the account's e-mail: Neon Auth does not support it yet. Parked as a triage stub for when it does.
- Showing the address to a professional after a confirmed booking, and asking for it at confirmation when it is missing: candidature-et-reservation (D-15).
- Showing the context line to professionals: demande-de-garde and candidature-et-reservation.
- The family's requests and past gardes on her home: demande-de-garde and cycle-de-garde-et-annulation.
- The communes a professional serves (onboarding-professionnelle) and public per-commune pages (recherche-et-fiches-publiques): they reuse `src/lib/communes/`, which this run only builds.
- Family verification (D-27), phone verification by SMS, favourites as a separate feature.
- Account deletion, data export and the rest of RGPD self-service.
- Geocoding, a map, or checking that a street exists (D-11).
- Scope decisions this run neither builds nor changes: D-1 to D-8, D-10, D-12, D-14, D-16 to D-18, D-21 to D-23, D-25, D-26.
