# Plan: messagerie

Build's execution plan in passes — each pass one layer of the change, in the order it lands, so
a session that resumes mid-build sees where it is. Written by the advisor pass (Define, or
Build's first act on `sonnet` after reading the spec), executed pass by pass, and rewritten when
reality disagrees with it — never left describing a plan that was abandoned.

## Passes

1. **Schema and migration** — `src/db/schema.ts`: the enums `message_author` (`berceo`, `famille`, `professionnelle`) and `berceo_message` (`amorce`, `bonne_garde`); the tables `conversations` (unique `application_id`, the two read markers, `last_message_at`, the two list indexes) and `messages` (client-supplied uuid key, the three checks, `(conversation_id, created_at)` index); `npm run db:generate -- --name messagerie`; append the backfill (`INSERT … SELECT` from `care_request_applications` with an `amorce` at `answered_at`, and a `bonne_garde` at `bookings.confirmed_at`) to the generated SQL; commit `drizzle/`. Load `.icm/skills/database-migration/` — done when: one migration, the journal test passes, the backfill is idempotent against an empty database, and no other open run holds a migration.
2. **The rules module** — `src/lib/messagerie/rules.ts` (pure): `isConversationOpen(request, now)` (not `annulee`, now before night start + 11 h through `hasNightStarted`/`endTime` from `src/lib/demandes/rules.ts`), body validation (trim, 1 to 2 000), who is a party, unread for a viewer, « Lu » for the sender's last message, the banner positions (after the 3rd, 6th … people's message, never when the answer is `retenue`) — done when: unit tests cover each rule, the night boundary in Europe/Brussels included.
3. **The data module** — `src/lib/messagerie/` (server-only): create a conversation with its `amorce` (called inside `answers.ts`' answer transaction, a no-op when the answer already has one), post `bonne_garde` (inside `bookings.ts`' accept transaction), the viewer's list with unread flags, one conversation for a party only (not found otherwise), mark read, send (party check, open check, `ON CONFLICT (id) DO NOTHING`, bump `last_message_at`), the unread count — done when: unit tests cover ownership (another family's or professional's id reads not found and cannot send), a closed conversation refusing a send, a duplicate id inserting once, and the re-answer reusing the conversation.
4. **E-mail** — `src/lib/email/templates.ts` and `src/content/emails.ts`: « [Prénom] vous a écrit », no message text, the link to the recipient's own conversation path; the send action schedules it with `after()` and key `message-<id>` only when the insert actually happened — done when: the template test renders it and a test proves a duplicate send schedules no second e-mail.
5. **Words** — `src/content/messagerie.ts` (lists, empty states, the conversation page, the two Berceo messages, the banner, « Lu », « Envoyer », the closed line, the errors, the entry-point labels) and « Messages » in `src/content/portal.ts`; quotes marked, the rest `@relecture Surya`; `src/content/messagerie.test.ts` on the catalogue's mechanical rules — done when: the catalogue tests pass.
6. **The pages and the shell** — `src/components/messagerie/` (list row, thread, Berceo message, banner, composer as a client component with its own uuid); `/espace/famille/messages` + `[id]`, `/espace/professionnelle/messages` + `[id]`; « Messages » with the unread count in `space-shell.tsx` / `portal-shell.tsx` and on the menu button (`mobile-menu.tsx`); the entry points on the family's answer cards and booking page and the professional's answered request cards and garde page; `routing.test.ts` if the routing guard lists paths — done when: on the preview at 360 px and on desktop a professional answers, both sides see the `amorce`, they exchange messages, each receives one e-mail per message, « Lu » and the unread count follow, the booking adds `bonne_garde`, and a conversation on a past night shows the closed line.
7. **Docs** — README « The conversation », the `AGENTS.md` routing row for `src/lib/messagerie/` and the pages — done when: both land in the PR.

## Risks

- **A conversation readable by someone who is not a party.** Signal: any read in `src/lib/messagerie/` not filtered by the viewer's user id (family) or profile id (professional). Guard: the ownership tests of pass 3; the page passes the session's identity, never an id from the URL alone.
- **One message, several e-mails.** Signal: the e-mail scheduled on a conflicting insert, or from a page load. Guard: schedule only on `rowCount === 1`; the idempotency key as a second net.
- **The backfill against UAT data.** Existing answers on `uat-berceo` get conversations; a withdrawn or declined answer on a past night gets one too (closed by time). Signal: `db:verify` red on the preview branch, or a duplicate on re-run. Guard: `WHERE NOT EXISTS` on `application_id`.
- **The header count's cost.** One aggregate query per signed-in page load. Signal: a slow portal. Guard: the `(family_user_id, last_message_at)` / `(profile_id, last_message_at)` indexes and a single `COUNT(*)` with `EXISTS`.
- **cycle-de-garde-et-annulation extends the closing rule** for a cancelled booking. Keep it one function in `rules.ts`.
