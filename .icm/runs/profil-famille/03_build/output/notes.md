## Notes for Release

- **Spec gap, decided in Build (D-38):** the spec says the list is "joined to Statbel's REFNIS codes". Statbel's download is behind a bot challenge no script passes, so the codes come from Eurostat's LAU list for Belgium (Statbel's codes, 2024) plus the 13 codes from the 2025 mergers listed in `scripts/communes/generate.py` (Antwerpen 11002, Pajottegem 23106, Wingene 37021, Tielt 37022, Nazareth-De Pinte 44086, Lochristi 44087, Merelbeke-Melle 44088, Lokeren 46029, Beveren-Kruibeke-Zwijndrecht 46030, Tessenderlo-Ham 71071, Hasselt 71072, Bilzen-Hoeselt 73110, Tongeren-Borgloon 73111). The counts check (581 − 29 + 13 = 565, bpost's own count), but the 13 codes need a hand check against Statbel's REFNIS list. Matching only needs the codes to be consistent inside the app, so a wrong code there breaks nothing until an external join.
- **Names (D-39):** bpost's French file gives Dutch names for Brussels and Mouscron; the shown names are Eurostat's French forms. A Brussels sub-locality keeps bpost's name (e.g. « 1020 Laken (Bruxelles) »); searchable either way. Surya may want a word on it.
- The combobox ships the list to the browser (≈116 KB raw, much less gzipped) on the profile page only.
- `getAuth().updateUser` is the only Neon Auth call new here; on failure it logs `[famille] Neon Auth name not updated` and the save still succeeds.
- Look closely at: the forged-value path (`parseLocalityValue`), the batch in `saveFamilyProfile`, and the guard test's allowed list.
