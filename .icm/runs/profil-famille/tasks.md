# Tasks: profil-famille

The queue, with a definition of done per item. Ticked by the stage that finishes the item —
a human checkbox, never a script's. The definition of done is seeded from the spec's
acceptance criteria when the run is opened; the queue is Build's own, one line per commit-sized
step, so a resuming session can pick up the first unticked line.

## Definition of done

- [ ] A signed-in parent opens `/espace/famille/profil` from the "Mon profil" entry in the portal navigation, on a phone (360 px wide, no horizontal scroll) and on a desktop.
- [ ] A professional or an admin who opens `/espace/famille/profil` is sent to their own space, and a signed-out visitor is sent to sign in with a return to the page; `routing.test.ts` covers the path.
- [ ] The form is prefilled with the parent's prénom, nom and téléphone. Saving new values updates the `users` row and `updated_at`, and the new first name is used by the space's greeting.
- [ ] The e-mail is shown and cannot be edited, with a line saying it cannot be changed for now; the server action ignores any e-mail field sent to it.
- [ ] Typing a postcode prefix (« 105 ») or a name, accents and case ignored (« ixel »), lists the matching localities; picking « 1050 Ixelles » and saving stores that postcode, locality and Ixelles' INS code.
- [ ] A commune value that is not an entry of the list, sent directly to the server action, is refused with a field error and nothing is saved.
- [ ] Saving without a commune is refused with a field error. Saving with a commune and no address succeeds; a rue without a numéro, a numéro without a rue, or a boîte alone is refused with a field error.
- [ ] A family completes the commune and address once, returns later, sees them prefilled, edits them, and the edit is saved.
- [ ] The context line accepts at most 300 characters and is refused above that, both in the form and by the database; the hint asks not to include health information or children's names.
- [ ] `/espace/famille` shows the "Complétez votre profil" block with a link to the profile while no commune is saved, and no longer shows it once one is.
- [ ] The address columns are read only inside `src/lib/famille/`: a test fails if another file names them, and a unit test proves the commune-only reader returns no address field. No page, action, route or API a professional or a visitor can reach returns the address.
- [ ] The server action saves only the signed-in parent's own rows, whatever user id the form carries, and refuses any non-parent session.
- [ ] `src/lib/communes/` contains the generated list with both sources and the date in its header, a script in `scripts/communes/` regenerates it, and tests cover search by postcode prefix, search by name, lookup and the INS code of a sample locality in each region (Brussels, Wallonia, Flanders).
- [ ] The migration adding `family_profiles` is generated by drizzle-kit, the journal test passes, and a preview build applies it to its own Neon branch through `vercel-build`, with `db:verify` passing.
- [ ] Every visible word of the profile page and the home block lives in `src/content/`; each entry not verbatim from the guide carries `@relecture Surya`; no entry uses `!`, `…` or `—` (a catalogue test enforces it).
- [ ] The e-mail-change triage stub exists under `.icm/intake/triage/`, naming the Neon Auth limitation and what the change must do once it is supported.
